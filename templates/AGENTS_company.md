## 公司專案規則

> 公司規則版本：2026-10-21

### 環境與同步
- `.venv`、`runtime\`、大型壓縮檔不進 Git，每台各自建立；`.venv` 用 GitSync 的「管理專案 / .venv」建立或更新。
- 寫給管制機執行的程式：Python 3.11（管制機用 `py -3.11` 建 venv，執行一律用 `.venv\Scripts\python.exe`，不直接呼叫 `python`）；管制機主控台字碼頁是 950，讀寫檔案明確指定 `encoding="utf-8"`，給 Excel 開的 CSV 用 `utf-8-sig`。
- 管制機上的指令只用 cmd、PowerShell 5.1 與免安裝工具。

### 內網與發布
- 開發機看不到內網的共用磁碟、NAS 與網站。連線位址與路徑寫在設定檔，開發機用專案內附的範例資料測試；依賴內網的功能標示「需在管制機驗證」。
- Python 啟動器（`Launcher.bat`／`Launcher.vbs`）依序使用：專案內 `.venv\`（使用者自己的開發機、管制機）→ 專案內 `runtime\`（同事電腦，由 `python_env.zip` 解壓）。**不自動建立 `.venv`**，沒有 `.venv` 的電腦一律視為同事電腦；兩者都找不到時跳出對話框說明原因。
- `python_env.zip` 由使用者用 `.venv` 手動打包，以隨身碟或公司雲端硬碟提供給同事，不進 Git。
- 不是 Python 的同事工具，優先做成單一 HTML 檔或 PowerShell 視窗工具。
- 內網網頁用到的 JS/CSS 函式庫一律下載放進專案，不依賴外部 CDN（同事電腦能不能連 CDN 無法保證）。
- 發布到內網伺服器（網站資料夾、NAS）一律用 GitSync 的「網頁發布」分頁（比對差異、覆寫前備份、可還原），不另寫會直接覆寫伺服器的腳本。
- 不主動刪除共用磁碟、伺服器上的檔案（包含線上的舊備份）；使用 `robocopy /MIR`、`/PURGE` 這類會刪除目的地檔案的參數前，先說明影響並取得同意。

### 成品的防毒相容
成品會在管制機與同事電腦上執行，這些電腦都有端點防毒的行為監控。開發機上寫程式、測試不受限制，但**成品本身**必須符合：
- 執行時不可動態產生腳本檔（.bat、.cmd、.ps1、.vbs）再執行；需要的腳本作為專案檔案一起提供。
- 只有「使用者雙擊的啟動器」（.bat／.vbs）可以呼叫 PowerShell，並且只執行專案內既有的 `.ps1`；Python 等程式在執行中不另開 PowerShell 或 cmd 去跑腳本。
- 不使用常被惡意程式利用的系統程式：`mshta`、`certutil`、`bitsadmin`、`regsvr32`、`rundll32`、`wmic` 等。
- 不需要管理員權限：不寫入 `C:\Program Files`、`C:\Windows`、`HKLM`，不修改防火牆或系統設定；輸出寫在專案資料夾或使用者資料夾。
- 不在執行中下載並執行外部程式；需要連外網的功能，先請使用者在管制機實測能不能連。
- `.ps1` 只用 PowerShell 5.1 語法。
- 防毒相容性只能在管制機實測：由使用者分別雙擊 `.bat` 與 `.vbs` 啟動，確認沒有被攔截；回報時標示「需在管制機驗證」。

### 除錯與回報
- 程式把錯誤寫進 log 檔（完整錯誤訊息、程式版本、執行環境），並在畫面上顯示 log 位置；程式要有版本號，每次修正遞增。
- 開發機正常、管制機出錯時，依序檢查：寫死的路徑、編碼（cp950／UTF-8）、套件版本、檔案鎖定／權限／防毒攔截、同步漏檔（是否忘了 commit）。
- 給使用者帶到另一台執行的內容要能獨立閱讀：註明在哪台電腦、開什麼視窗（cmd／PowerShell）、要跑的指令、預期結果、出錯時停下來回報；只查詢的指令標明「不會改動任何檔案」，會改動或刪除的步驟先安排備份。
- 交付修正：給完整檔案，或「找這段 → 換成這段」（要找的內容必須能唯一搜尋到），並附上驗證步驟。

### 跨專案規範審查
只適用於本檔「業務規則」寫了「本專案參與跨專案規範審查」的專案，沒寫的專案略過本節。公司工作區（本專案的上一層資料夾）裡同樣寫了這一行的專案，就是「參與審查的其他專案」。
- 查證、整理或做成程式的**規範內容也能用在其他參與專案**時，列進審查文件，並在回覆最後提醒：「已列入跨專案規範審查第 N 項，待審查」。
- 要列的情況：另一個專案引用同一份規範（或舊版）；發現規範的寬嚴差異、筆誤、互相不一致，且其他專案用到同一條；做出可重複使用的資料或判定核心；使用者確認的呈現原則或用語其他專案也適用。
- 審查文件：每個參與專案各放一份完整的 `docs/跨專案規範審查.md`，**內容必須完全相同**，跟著各專案的 Git 跨電腦同步。每項一列、編號遞增、不刪舊列；欄位：編號｜發現日期｜來源專案｜發現內容｜出處（規範名稱＋版次＋條號）｜可能受影響的專案與檔案｜建議｜狀態。
- 同時更新：新增或修改任何一列時，同一次工作就把所有參與專案的這份檔案改成一樣，並各自 commit（只動這份檔案）。動手前先比對各份是否相同；不一致時先列出差異請使用者決定，不要自行合併。
- 狀態：`待審查` → 使用者決定後改為 `要導入`、`不導入` 或 `已導入（日期）`。除了審查文件本身，只列出、不直接修改其他專案；決定「要導入」後，到該專案另開工作時再改。
- 開始工作時，若審查文件有目標是本專案的 `要導入` 項目，先提醒使用者。
- 判斷其他專案用到哪些規範：讀各參與專案的 `AGENTS.md`、`README.md`（與 `PROGRESS.md`、`docs/` 的參考文件清單）；看不出來時寫「可能相關，需使用者確認」。
