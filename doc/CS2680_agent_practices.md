# CS2680 重點摘要：給 AI 編碼代理的工作守則

> 來源：Harvard CS2680 Modern AI Systems（Juncheng Yang, Fall 2026）第 2、3、4、6 講與「Cost-effective agents」講義，https://cs2680.com/
> 用途：給 Claude Code、Antigravity 等編碼代理當參考。這是課程重點的整理，不是原文。

## 1. 代理怎麼運作
- 一句使用者指令 = 多輪「組裝上下文 → 模型提出動作 → 執行工具 → 結果放回上下文」的循環
- 每一輪都會重送整個上下文；上下文越長，成本、延遲越高，準確度越低
- 開始打字前，系統提示、工具、規則檔、skill 描述就已佔用一萬多 token
- 程式庫不會整包送給模型，代理用 grep/glob/read 按需取片段

## 2. 上下文管理
- 上下文是有限資源：輸入越長準確度越低；放在中段的資訊最容易被忽略
- 管理手段由輕到重：
  1. **控管進入**：精準查詢、只取需要的欄位、截斷冗長輸出
  2. **外放**：計畫、筆記寫到檔案，需要時再讀
  3. **刪減歷史**：去除重複、遮蔽舊的工具輸出
  4. **壓縮摘要**：最後手段，會遺失細節
- 五種上下文失敗：錯誤被當成事實（Poisoning）、模仿自己過去的動作（Distraction）、無關資訊誤導（Confusion）、新舊資訊衝突（Clash）、真正目標被替換（Drift）

## 3. 規則檔（CLAUDE.md / AGENTS.md）
- 每次對話都會載入 → 每個 token 都是每次都要付的租金
- 每檔 200 行內；標題加條列；規則具體；不可矛盾或過時
- 該寫：測試/建置指令、硬性限制、AI 無法便宜推斷的事實（目錄、坑）
- 不該寫：語言或框架常識、formatter 已處理的風格、長篇說明、機密
- 太長就拆成 `.claude/rules/` 一主題一檔，用 `paths:` 只在相關時載入（本倉庫的換算見第 0 節）
- 過時的記憶比沒有更糟；把規則檔當程式碼審查、修剪、版本控管

## 4. 擴充機制分工
| 機制 | 解決的問題 | 例子 |
|---|---|---|
| Skill | 怎麼做一件事（知識與流程） | 依公司 API 規範寫程式、部署步驟 |
| MCP | 連到外部資料與動作 | 讀 Jira、查資料庫 |
| Hook | 在固定時機自動執行、強制 | 每次編輯後格式化、阻擋寫入正式環境 |
| Plugin | 打包分發以上三者 | 跨專案共用整套設定 |

- Skill 的 description 決定何時被叫用；內文只在執行時載入
- 有副作用的 skill 應要求使用者明確觸發
- 好的流程型 skill 包含：進入條件、必要動作、禁止動作、人工核准關卡、驗證要求、下一個 skill

## 5. 多代理
- **平行代理**：多個獨立任務各用一個 git worktree，換取時間而不是品質
- **子代理**：把冗長、可獨立、只需回傳摘要的工作交出去；主對話保持乾淨
- **留在主對話**：需要來回討論、彼此共享上下文、要求速度的小改動
- **代理團隊**：成本最高，只在工作需要彼此討論時使用
- **規格檔分工**：用 SPEC.md / 進度文件記錄步驟，新對話讀檔即可接手

## 6. 可靠性
- 每步 95% 成功，50 步全對的機率約 8%：錯誤會累積 → 任務要切短
- 規格失敗與對策：
  | 規格寫法 | 代理行為 | 對策 |
  |---|---|---|
  | 「修好登入 bug」 | 修錯了另一個 | 指名檔案、症狀、重現方式 |
  | 「讓測試通過」 | 刪掉失敗的測試 | 禁止改測試，審查 diff |
  | 「加快搜尋」 | 弄壞公開 API | 寫明哪些不能變 |
  | 「整理 parser」 | 一直重構停不下來 | 給結束條件與停止規則 |
  | 「最小改動又要涵蓋所有情況」 | 默默放棄邊界情況 | 明確排序目標優先順序 |
- 模型常見失敗：呼叫不存在的函式、違反指示、沒驗證就宣告成功、長任務中推翻自己先前的修正
- 對策：要求證據（測試輸出）、對照計畫檢查每個動作、重新讀取現況、拆成短任務

## 7. 成本
- 衡量單位是「整個任務」：含重試、驗證、人工修正，不是單次回覆
- 固定不變的內容放在提示開頭，維持快取命中；不要在對話中途改規則檔
- 規格清楚、工具輸出精簡，比縮短提示更省：避免亂繞與後期重做
- 驗證值得做的前提：它攔到的錯誤成本大於執行驗證的成本

## 8. 給代理的行為守則（可直接遵循）
1. 開工前先列假設；有歧義先問
2. 先規劃（SPEC.md），等核准再實作；一次一個步驟
3. 只讀、只改任務相關的檔案
4. 不改測試來讓測試通過；不違反規則檔中的「不可更動」
5. 宣告完成前必須實際執行驗證並附上輸出
6. 除錯先重現、列假設、驗證，再修改；修兩次失敗就停下寫摘要
7. 不確定 API 是否存在時查實際文件或原始碼
8. 刪除、覆寫、推送、對外連線前先詢問
